# Week 5 Reproducibility: Short-read polishing of *Bacillus subtilis* BEST3145

## Introduction

Reproducibility in computational biology means that another researcher should be able to obtain the same public data, recreate the software environment, execute the same commands, and recover the same scientific outputs. This repository demonstrates that principle with a small downstream genome-polishing analysis.

The workflow uses a complete genome and paired-end Illumina reads from the same deposited *Bacillus subtilis* BEST3145 BioSample. The Illumina reads are mapped to the original genome, used to polish that genome with NextPolish, and then mapped again to the polished assembly. The original and polished assemblies are compared using mapping statistics, assembly statistics, and Merqury k-mer quality metrics.

Long-read assembly, Porechop, Flye, and Medaka are intentionally excluded so the analysis remains small enough for the Week 5 reproducibility exercise.

## Objective

The objective is to provide a Bash-based workflow that another Linux user can reproduce from public data without needing the raw input files in the GitHub repository.

The workflow should:

- retrieve the public reference and reads automatically;
- use an assembly and Illumina run from the same BioSample;
- map the reads to the original genome;
- polish the genome using short reads with NextPolish;
- remap the same reads to the polished genome;
- compare the original and polished assemblies with mapping and Merqury metrics;
- record each stage in a separate log file; and
- verify a new run against canonical SHA-256 checksums.

## Research question

**Does short-read polishing with NextPolish change measurable quality metrics of the public *Bacillus subtilis* BEST3145 genome assembly when the same paired-end Illumina reads are used to evaluate the assembly before and after polishing?**

## Public data

| Resource | Accession |
|---|---|
| Organism/strain | *Bacillus subtilis* BEST3145 |
| Assembly | `GCA_019704475.1` |
| Complete chromosome | `AP024628.1` |
| BioSample | `SAMD00163116` |
| Paired-end Illumina run | `DRR172337` |
| BioProject | `PRJDB8028` |

The analysis uses the first **300,000 SRA spots** from `DRR172337` to keep the exercise small. Those reads are regenerated by the workflow; they are not stored in GitHub.

## Methods overview

The analysis performs seven stages:

```text
00_fetch_data
      ↓
01_map_original
      ↓
02_nextpolish
      ↓
03_map_polished
      ↓
04_merqury
      ↓
05_summary
      ↓
06_checksums
```

### 1. Data retrieval

`AP024628.1` is downloaded from NCBI Nucleotide and saved as:

```text
input/reference.fasta
```

The first 300,000 SRA spots from `DRR172337` are extracted with SRA Toolkit and saved as:

```text
input/reads_R1.fastq
input/reads_R2.fastq
```

### 2. Mapping to the original assembly

BWA indexes the original reference and `bwa mem` aligns the paired Illumina reads. SAMtools sorts and indexes the BAM file and calculates:

- total reads;
- primary mapped percentage;
- properly paired percentage;
- mean depth; and
- breadth of coverage at >=1x.

### 3. Short-read polishing

NextPolish is run with short-read task `1212`. The polished assembly is saved as:

```text
outputs/polished.fasta
```

### 4. Mapping to the polished assembly

The exact same Illumina reads are mapped to the polished genome with the same BWA/SAMtools procedure.

### 5. Merqury evaluation

Meryl creates a read k-mer database using `k=21`. The same database is used by Merqury to evaluate the original and polished assemblies. QV, estimated error rate, and k-mer completeness are retained.

### 6. Summary

Assembly, mapping, and Merqury metrics are combined into:

```text
outputs/summary.csv
```

### 7. Checksums

A new run writes its hashes to:

```text
CHECKSUMS.generated.txt
```

The repository's committed:

```text
CHECKSUMS.txt
```

is the **canonical checksum reference** and is never overwritten by `run.sh`. This distinction is essential: an independent rerun must be compared against the original canonical hashes rather than replacing them with its own hashes.

## Software environment

The Conda environment is defined in:

```text
environment.yml
```

It includes pinned versions of the main tools used by the analysis, including SRA Toolkit, BWA, SAMtools, NextPolish, Meryl, and Merqury.

## Recommended one-command setup

From a fresh Linux clone:

```bash
git clone https://github.com/SachidaPokhrel/Replicability.git
cd Replicability
bash setup_and_run.sh
```

`setup_and_run.sh`:

1. checks for an existing Conda executable;
2. if Conda is missing, downloads a pinned Miniforge installer;
3. verifies the Miniforge installer SHA-256;
4. installs Miniforge locally without `sudo`;
5. creates/updates a project-local Conda environment at `.conda-env/`;
6. runs `run.sh`; and
7. runs `verify.sh` against the canonical `CHECKSUMS.txt`.

The bootstrap currently targets Linux. The canonical analysis used 4 threads.

## Manual setup

If Conda is already available and you prefer to run the workflow manually:

```bash
conda env create -f environment.yml
conda activate week5-best3145
bash run.sh
bash verify.sh
```

## Reproducibility verification

After the analysis has regenerated the public input files and scientific outputs, run:

```bash
bash verify.sh
```

`verify.sh` compares every file listed in the committed canonical `CHECKSUMS.txt` using:

```bash
sha256sum -c CHECKSUMS.txt
```

A successful independent run should report `OK` for all three input files and every scientific output.

Do **not** run `verify.sh` before generating the input data: the raw public FASTA/FASTQ files are intentionally excluded from GitHub.

## Main result from the canonical run

The canonical analysis produced:

| Assembly | Total bp | Primary mapped % | Properly paired % | Mean depth | Breadth >=1x % | Merqury QV | Merqury completeness % |
|---|---:|---:|---:|---:|---:|---:|---:|
| Original | 4,217,110 | 99.52 | 99.17 | 39.254981 | 99.922791 | 51.4374 | 99.8997 |
| Polished | 4,217,111 | 99.52 | 99.17 | 39.254982 | 99.922791 | 51.4374 | 99.9001 |

The NextPolish result differed from the original assembly by one base in total length. Mapping metrics and Merqury QV were essentially unchanged, while Merqury completeness increased slightly.

## Reproducibility statement

This repository is designed so that another Linux Bash user can start from public accession numbers, recreate the software environment, regenerate the input data, rerun the complete downstream analysis, and compare the resulting files against a canonical byte-level checksum reference.
